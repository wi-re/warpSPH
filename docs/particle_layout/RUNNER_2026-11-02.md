## Step and hook ownership

Admission checks run before output creation: periodic fluid-only CompSPH/CRK,
eager list mode, native RHS, and a registered one-step RK/DIRK/coupled tableau.
Implicit methods require non-compatible energy and the qualified FD-JFNK route.
The runner does not supply prior-step/FSAL/multistep memory. Unsupported history
methods, custom RHS, sources, walls, grids, graphs, trajectory storage and restart
are refused. `MortonStepper.validate` shares the state/config eligibility checks
with the direct adapter without sorting or publishing a resource.

Each step computes in one fixed private order. Public results and stages return
in that step's input order. An unsuccessful integrator status stops before
publishing the candidate state to hooks or adopting a layout. Coverage invalidation
still propagates and unwinds the complete attempt; automatic envelope renewal is
not implemented.

For successful steps, post-step hooks, timestep selection, diagnostics, frame
consumers and stop checks consume the current input order. Then adoption moves
the continuation to compute order while preserving the neighbor list and its build
anchors. The exposed `ctx.scratch['lastStageUpdate']` is mapped to the adopted
state's rows; retained historical stages keep their explicit evaluated UIDs.
Subsequent list rebuilds inside a step keep that step's layout. Stale boundary
lists can trigger a new sort on the next step.

Case hooks opting into this policy must associate persistent particle data by UID.
Caching a storage index or an unlabelled column in a closure/scratch dictionary is
not automatically adapted. Global reductions and geometry/UID-based hooks work
across adoption. The runner uses CFL timestep selection and has no embedded-error
accept/reject controller; a successful numerical status is its acceptance boundary.
This slice adds no adaptive rejection policy.

## Output and timing

Initial, intermediate and final state files use ascending UID order, including
stage particle fields and any requested stage adjacency. Scalar Python/NumPy
metadata, including `frame_num` and ordinary case parameters, has no particle axis
and is accepted. Unlabelled arrays or nested extra data still require an explicit
axis adapter and fail before a frame is opened. Initial metadata is checked before
creating the run directory. Later extras are checked at their frame boundary.

The legacy fixed-roster trajectory writer and checkpoint resume remain blocked
for this runner option. Per-state export qualification does not qualify restart.
Graph/pipelined output remains a separate gate.

`stepTime_ms` includes integration and layout adoption; `layoutAdoption_ms` also
records adoption separately. Hooks, diagnostics and file I/O are outside that step
timer. Live Morton progress is emitted after adoption so it uses the same total.
